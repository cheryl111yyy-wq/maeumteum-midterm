# Prompt Log

## 본문 8페이지와의 연결

| 본문 쟁점 | 관련 기록 | 최종 처리 |
|---|---|---|
| 생활 태그와 메모를 필수로 할 것인가 | 기록 5 | 선택 사항으로 유지 |
| 모든 생활 태그를 홈에 보여 줄 것인가 | 기록 1, 기록 7 | 홈에는 일부만, 전체는 기록 화면에 표시 |

기록 4와 기록 6은 `[탐색]`으로 표시했습니다. 주간 리포트의 인과 해석과 앱 내부 AI 분석을 최종 본문에 넣지 않은 이유를 남긴 탐색 기록입니다.

## 기록 1. UX/UI 반론 검토

- 날짜: 2026-10-28
- 도구: Codex
- 목적: 기록 흐름, 생활 태그 위치, 주간 리포트 문구의 약점을 점검

요청:

```text
마음틈의 UX/UI 반론자가 되어 주세요. 장점은 반복하지 말고 다음 다섯 가지의 약점과 반례만 검토해 주세요.
1. 오늘 화면에 감정과 생활 태그가 함께 있을 때 정보가 과밀해지는가
2. 생활 태그와 메모가 선택 사항일 때 기록의 맥락을 이해하기 어려운가
3. 최근 7일 기록이 적을 때 결과를 과도하게 일반화하는가
4. Loading, Error, Empty 상태가 실제 시연을 충분히 지원하는가
5. 근거가 부족한 주장은 무엇인가
```

AI 반론 요약:

1. 작은 화면에서 전체 태그와 감정 선택이 함께 있으면 화면이 길어질 수 있습니다.
2. 글 입력이 모두 선택이면 나중에 기록의 상황을 이해하기 어려울 수 있습니다.
3. 기록이 적은데 `가장 자주 남긴 감정`을 보여 주면 결과가 지나치게 확정적으로 보일 수 있습니다.
4. 상태를 PPT 그림으로만 보여 주는 것은 구현이 아닙니다.
5. `대학생에게 더 적합하다`는 현재 설계 방향이며 검증된 경쟁 우위가 아닙니다.

반영:

| 문제 | 처리 | 근거 |
|---|---|---|
| 홈 정보 과밀 | 자주 쓰는 태그만 홈에 두고 전체 선택은 기록 화면으로 이동 | P04, P08 |
| 선택 메모로 맥락 부족 | 메모는 선택으로 유지하고 기록 상세에서 날짜·감정·태그를 함께 표시 | P03, P05 |
| 적은 기록의 과잉 해석 | 3일 미만이면 데이터 부족 안내 표시 | P09 |
| 상태가 그림으로만 존재 | 실제 GET 요청과 상태 전환 메뉴 구현 | P01, P09 |
| 차별성 미검증 | 발표와 문서에서 설계 가설로 표시 | 연구 결과를 임의로 만들지 않음 |

최종 변화:

- 홈에 테마 설정이나 불필요한 설정 메뉴를 추가하지 않았습니다.
- 주간 리포트는 `json-server`의 `weeklyReport` 모의 결과를 사용하고 `예시 데이터 포함`을 표시합니다.
- 오류와 빈 상태를 실제로 조작할 수 있는 화면으로 구현했습니다.

## 기록 2. 여섯 관점 피시본 검토

- 날짜: 2026-10-28

요청:

```text
여섯 관점 피시본이 `사용자가 바쁘다`는 말을 여섯 번 바꾼 것에 불과한지 검토해 주세요.
경쟁 앱 리뷰, 화면 상태, 사용자 테스트로 확인할 수 있는 원인을 구분해 주세요.
```

AI 반론:

- `바쁘다`는 감정이나 맥락일 뿐 근본 원인이 아닙니다. 프로세스, UI, 콘텐츠, 기기, 피드백으로 나누어야 합니다.
- 감정 선택의 어려움과 앱 접속 실패는 서로 다른 문제입니다.

반영:

- 피시본의 중심 문제를 `기록 과정의 입력 부담 가능성`으로 정했습니다.
- `필수와 선택의 구분이 불명확함`만 5 Whys로 깊게 분석했습니다.
- 접속 실패는 P01·P09의 상태 설계 문제로 분리했습니다.

## 기록 3. 한국어 문구와 해석 경계

- 날짜: 2026-10-28

요청:

```text
한국어 문구가 매일 기록을 강요하거나 감정 기록을 심리 진단처럼 보이게 하는지 검토해 주세요.
필요한 문장은 중립적인 표현으로 바꿔 주세요.
```

반영:

- 연속 기록을 강요하는 표현을 사용하지 않았습니다.
- `기록할 수 있어요`, `선택 사항이에요`처럼 선택 가능한 표현을 사용했습니다.
- 주간 리포트에 `특정 상황이 감정의 원인이라는 결론은 내리지 않아요`를 표시했습니다.
- 제품 범위를 감정 기록과 자기 관찰로 한정했습니다.

## 기록 4. [탐색] 7일 리포트의 해석 범위

- 날짜: 2026-10-28
- 목적: 7일 기록에서 감정의 원인을 설명하는 것이 적절한지 검토

요청:

```text
7일 감정 기록으로 특정 사건이 감정의 원인이라고 말할 수 있는지 반론해 주세요.
인과관계로 오해될 위험을 줄이면서도 회고 가치를 유지하는 표현을 제안해 주세요.
```

AI 반론:

- 7일은 작은 표본이므로 함께 나타난 태그와 감정을 인과관계로 볼 수 없습니다.
- `때문에`, `원인`, `영향` 같은 표현은 시스템의 추정을 사실처럼 보이게 할 수 있습니다.
- 기록이 적을 때 결론을 만들면 제품의 중립적인 위치와 충돌합니다.

반영:

- 감정의 원인을 설명하지 않고 기록 일수, 주요 감정, 주요 태그와 중립 문장만 표시했습니다.
- 기록이 3일 미만이면 데이터 부족 안내를 표시합니다.
- 앱 내부 AI 감정 분석은 구현하지 않았습니다.

## 기록 5. 생활 태그와 메모는 필수인가

- 날짜: 2026-10-28
- 목적: 기록의 완성도와 시작 부담을 비교

요청:

```text
주간 리포트의 정보를 늘리기 위해 생활 태그와 메모를 필수로 하는 것이 적절한지 반론해 주세요.
바쁜 학생, 기억 부족, 입력 정확성에 미치는 영향을 설명하고 구현 가능한 대안을 제시해 주세요.
```

AI 반론:

- 필수 입력은 빠른 기록을 막고 선택 정보를 시작 조건으로 바꿉니다.
- 상황이 기억나지 않을 때 임의로 입력할 가능성이 있습니다.
- 감정만 필수로 두고 태그와 메모를 명확한 선택 항목으로 표시하는 편이 안전합니다.

반영:

| 쟁점 | 처리 | 근거 |
|---|---|---|
| 태그와 메모 필수화 | 선택으로 변경하고 제목 옆에 `선택` 표시 | P03, P05, P08 |
| 감정 없이 제출 | 짧은 오류와 수정 방법 제공 | P05, P09 |
| 메모 길이 | 120자로 제한하고 작성하지 않아도 완료 가능 | P08 |

최종 변화:

- 감정 1개만 필수입니다.
- 태그와 메모는 비워 둘 수 있고 태그는 다시 눌러 해제할 수 있습니다.
- 기록 화면, PPT와 발표 스크립트는 모두 `감정 하나로 기록 완료`라는 기준을 사용합니다.

## 기록 6. [탐색] AI는 제품 기능인가 디자인 반론자인가

- 날짜: 2026-10-28
- 목적: 디자인 과정의 AI 사용과 앱 내부 AI 기능을 구분

요청:

```text
AI를 앱 안의 감정 분석 기능으로 넣는 것과 디자인 검토자로 사용하는 것의 차이를 검토해 주세요.
데이터 신뢰성, 개인정보, 과제 범위, Flutter 구현 부담을 기준으로 판단해 주세요.
```

AI 반론:

- 적은 감정 기록으로 신뢰할 수 있는 심리 분석을 제공하기 어렵습니다.
- 앱 내부 AI는 개인정보, 외부 서비스, 비용, 예측 불가능한 출력의 위험을 늘립니다.
- 과제에서는 Prompt Log와 셀프 논증으로 AI 활용을 설명할 수 있습니다.

반영:

- 앱 내부 AI 감정 분석은 제외했습니다.
- AI는 디자인 반론자와 문서 검토 도구로만 사용했습니다.
- 주간 리포트는 `json-server`에 미리 정한 모의 결과와 중립 문구를 표시합니다.

## 기록 7. 홈 화면의 태그 단계 검토

- 날짜: 2026-10-28
- 목적: 모든 생활 태그를 홈에 보여 줄지 결정

요청:

```text
모든 생활 태그를 홈에 표시하는 안을 정보 구조와 모바일 사용성 관점에서 반론해 주세요.
개인화에 도움이 되는지, 감정 선택을 약화하는지, 선택 태그가 필수처럼 보이는지 확인해 주세요.
```

AI 반론:

- 모든 태그가 한 화면에 나오면 홈이 `빠른 시작`이 아니라 `전체 옵션 목록`이 됩니다.
- 태그의 개인화 가치는 유지하되 전체 선택은 사용자가 상황을 입력하는 기록 화면에 두는 편이 좋습니다.
- 홈에는 자주 쓰는 일부 태그만 보여 주고 전체 목록은 기록 화면에서 제공해야 합니다.

반영:

- 홈에는 감정 선택과 자주 쓰는 태그 일부를 표시합니다.
- 전체 태그는 기록하기 화면에서 선택합니다.
- P04, P07, P08에 따라 정보 위치와 노출 시점을 분리했습니다.

## 제출 메모

이 문서는 디자인 검토에 사용한 요청, AI 반론의 요약, 수용·수정·폐기 판단과 실제 화면 변화를 기록합니다. AI가 생성한 결과를 그대로 제출하지 않고, 프로젝트 기준과 근거에 따라 다시 판단한 내용을 남겼습니다.
